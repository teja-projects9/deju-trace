Customizing

The slider button in the header opens Customize: which columns are shown, how tightly the rows are packed, the theme, which tab the report opens on, and what starts folded. Those choices are yours alone. They are kept in this browser and not written back into the file, so the copy you forward still opens the way it was exported.

What a report opens with is set when it is exported, in the plugin's Export dialog, along with which tabs are written into the file at all. A tab left out there is not in the document and Customize cannot bring it back.

Filters, the time threshold and Essential/Full are deliberately not in that panel. They change which calls you are looking at rather than how they look, so they stay in the toolbar where they are visible.

Filtering

The box beside the trace point filters whichever tab is in front, and each tab keeps its own query, so narrowing the tree down to one class does not also empty the Flame Graph. What a match means differs by tab, and the box says which as you switch: source text and SQL in Call Tree, a file or package name in Breakdown, a step label in Timeline, a title or detail in Findings, and in Flame Graph a regular expression over the step signature.

The Flame Graph's dropdown decides what a match brings with it. Match, with callers & callees keeps everything a matching step went on to call along with the chain of callers above it, so the diagram still says how the code got there. Match, callers only drops the callees, for when the shape of the calls into a layer is the question. Match by package matches on package names rather than signatures, which is the grouping a layered codebase is actually navigated by. A pattern that will not compile is used as plain text rather than reported as an error.

Findings

A handful of rules run over this recording and name what stands out in it: the same statement issued in a loop, one query that is most of the request, the frame that spent the time in its own code rather than in what it called, a method invoked far more often than the code suggests, and branches this request never took. Each card carries the numbers it was derived from and links to the step it came from, so nothing has to be taken on trust. The badge on the tab counts them.

Timeline

Where the wall clock went, in the order it went there. Each bar is one step: the solid part is time in that step’s own code, the faint part is time inside the calls it made. That split is the one the other views cannot show you, and it is what tells a slow method apart from a method that merely called something slow. Only the steps that own a meaningful share are listed; Show every step lifts that.

The caret on a row folds away everything that step called, however far down the run those calls are; Collapse all does it to the lot. Hovering a row reveals three actions: line opens the calling line in the IDE, sql opens the statement behind a query formatted and coloured in place, and step jumps to that frame in the Call Tree.

One honest limit: the agent records how long each call took, not when it started, so positions are derived by laying calls end to end in the order they ran. Durations and ordering are exact; a gap where the request sat idle cannot be shown, because nothing in the recording distinguishes it from work.

Breakdown

Time per file, slowest first. The bar has two parts: own code is the file's self time, the work its own lines did, and SQL is the time its queries spent in the database, charged to the method that issued them. Self time is the only additive measure here, a method's total time contains everything it called, so summing totals would count the same microseconds once per stack frame. Turning Include SQL off leaves only your own code, which is what you want when the question is which method to optimise rather than which query. This tab deliberately ignores the Files picker and your excluded types: it is an accounting of where the milliseconds went, and dropping a file would silently remove real time from the totals.

Flame Graph

The call tree drawn start to end, top to bottom in execution order, indented by depth. Each box is one invocation; the bar inside it is that call's total time relative to the whole run. Hover for the full signature and timing. It is the same data as the Tree view, laid out so a long chain of calls is visible at a glance.

Flame lays the same tree out by time instead: box width is duration, the entry point holds the floor and the stack grows upward, so the tallest column is the deepest chain and the widest box is the slowest call — the orientation Glowroot and every other JVM flame graph uses. Each box carries its time and its share of what is on screen. Clicking one makes it the new 100%; the trail above the diagram walks back out.

Colour carries identity, since most boxes are too narrow to label. Glowroot colours is the familiar warm ramp, Deju colours is this report's own palette, and By package gives up per-class identity for per-layer identity, which is the only thing that still reads once a run touches two hundred classes. Queries keep a fill of their own in every scheme, because telling a query from a method is the one distinction here that has to survive.

Save PNG and Save SVG both write whatever the diagram is showing right now, filters and zoom included. The SVG is vector, so it stays sharp however far it is zoomed, and it has no size ceiling — a diagram too wide for one image comes out whole, where the PNG saves only the visible part and says so.

Reading the tree

The numbered badge on each frame is its step number: the order the methods actually ran. A nested frame is a call made from the line above it, and called at :44 is the caller line that made it. The time on a frame is that call's total (inclusive); the time on a code line is that line's own (self) time.

Order fidelity. Method calls are in exact execution order. Lines within a method are shown in source order and merged across invocations, so a loop body appears once rather than once per iteration, and a method called twice shows the same lines under both frames.

Essential / Full. Essential folds calls into your excluded types (entities, DTOs, other data classes) into a single … N excluded calls row at the call site, the count and total time stay visible, and clicking the row expands it. A call is only folded when everything underneath it is also excluded, so a getter that turns out to trigger a lazy load stays on screen along with the query it caused. Excluded rows in the toolbar hides those summary rows altogether, once you no longer need to be told what was folded away. The Flame Graph and the Timeline fold the same types away by the same rule, and both carry a Show excluded button to put them back. Full shows every recorded call, repeats included: the ×N more folding that keeps an N+1 loop from flooding the default view is lifted here too. Choose the types in the IDE under Settings → Tools → Deju Trace, or with Excluded types… in the Deju tool window; the recording itself is always complete, so nothing here is ever lost. A nested class follows the class it lives in, so excluding a wrapper also excludes the builder generated inside it. In the Files view, excluded types are rendered like any other file but start folded shut.

Exclusions are applied when a report is written, so this file is a snapshot of the rules at that moment, changing them later never alters an existing report. Re-export the same run to apply new rules. Nothing about exclusions reaches the agent, so there is never anything to restart.

SQL. Executed queries appear at the line that issued them, formatted onto clause lines with their bound values left as ?, which is all that was ever recorded. A long statement is trimmed to three lines with Show full query to open it; the SQL button in the toolbar hides queries altogether when you want to read control flow on its own.

Files. The Files dropdown works in both views and means the same thing in each: unticking a file removes it from the Files view and hides its calls, and everything underneath them, from the Tree, so you can strip a trace down to the layer you care about. The traced method's own frame always stays, since hiding the entry point would empty the diagram. Data classes and generated code start ticked but folded shut, so the page opens on the code worth reading without anything being filtered out behind your back.

Open in IDE uses jetbrains:// links, which are handled by JetBrains Toolbox. If nothing happens when you click a line number, Toolbox is not installed, use Copy path in the Files view instead.

Sharing a spot. The address bar follows what you are looking at, tab, view, filter and the selected step, so the link in it opens this report where you are. The copy button on a step (or Shift+C) puts that one frame on the clipboard as plain text for a ticket or a chat.

Group repeats folds every repeat of the same call under one parent into a single row at its first occurrence. Unlike ×N more, which only catches repeats that happen to be adjacent, this catches a loop that alternates two calls and issues each of them two hundred times. Everything that is not a repeat keeps its exact position.

This report is a single self-contained file: no network calls, no remote resources, and no captured variable values. A large one stores its data compressed and unpacks it in the browser, which is why it opens a moment after it loads.
